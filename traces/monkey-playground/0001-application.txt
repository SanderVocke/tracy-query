Workload
--------

The QML MonkeyTester randomly and rapidly added/removed tracks and loops and
requested recording and playback transitions. The dummy backend ran at:

  sample rate: 48,000 Hz
  buffer size: 256 frames
  nominal callback period/budget: 5.333 ms

This is a deliberately chaotic workload, not a repeatable benchmark. The trace
uses detailed engine mode, so it contains considerably more zones than a normal
coarse capture.

Useful plots
------------

BackendWrapper plots include callback last/worst duration and budget overruns,
cycles/frames, pending/applied commands, graph arms/applies, schedule generation,
stale/stuck cycles, xruns, capture under/overruns, trace snapshot drops, and
buffer/sample-rate state.

Object plots include loop mode/position/next transition, channel mode, FX
active/ready state, MIDI-control queue state, and frontend refresh queue delay.

Final published values in this capture included:

  cycles / frames:             2,311 / 591,616
  commands applied:            2,939
  pending commands:            0
  graph arms / applies:        360 / 58
  schedule request / applied:  330 / 330
  stale cycles:                83
  stuck cycles:                1
  callback budget overruns:    0
  xruns:                       0
  capture under/overruns:      0 / 0
  trace snapshots dropped:     2,308

The high trace-snapshot drop count is expected evidence of this unusually busy
detailed monkey run: bounded diagnostic snapshots were coalesced/dropped rather
than blocking the realtime thread. Object/state plot history may therefore be
incomplete even though the direct Tracy zone hierarchy is present.

Indicative callback timings
---------------------------

For a steady 3-14 second portion (1,893 callbacks):

  mean:    148.6 us
  median:  147.4 us
  p95:     205.5 us
  p99:     242.5 us
  maximum: 1.922 ms

No callback exceeded the nominal 5.333 ms budget. The broader
engine.rt.driver.dummy zone includes control pumping outside Engine::run_cycle;
it had a 178 ms outlier during aggressive graph/control churn. Do not confuse
that whole-thread/control-path stall with callback DSP duration.

Suggested things to inspect
---------------------------

1. Select the engine-dummy-driver thread and follow
   engine.rt.driver.dummy -> callback -> cycle -> session.
2. Find the largest engine.rt.driver.dummy zones and correlate them with
   engine.control.* and engine.graph.* activity on the main/scheduler threads.
3. Compare engine.callback frame marks with frontend.refresh frame marks.
4. Inspect callback_worst_ns, stale_cycles, graph_applies, schedule generation,
   and trace_snapshots_dropped plots while the monkey mutates the graph.
5. Zoom into session detail to compare ports, channels, loops, composites,
   routing, MIDI, and FX work.

Caveats
-------

This was a headless dummy-backend debugging run. Mesa could not initialize the
hardware driver and emitted expected offscreen/software-rendering warnings.
Tracy may allocate, lock, change scheduling, increase memory use, or cause xruns
on a real JACK/CPAL callback. This trace is useful for exploring causal and
timing structure, but it is not an allocation-free or transparent realtime
measurement and should not be used as a hardware performance guarantee.
